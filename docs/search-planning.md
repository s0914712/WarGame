## 二、核心公式鏈

```
Wu  ──查表──►  W = Wu × Fw × Fv × Ff          掃掠寬度（文件2 五）
                     │
                     ▼
              C = W ÷ S                        覆蓋因子（文件2 七(三)）
                     │
                     ▼
              POD = f(C)                       發現機率（文件2 七）
                     │
                     ▼
              A = T × N × P × S                搜索五要素（文件2 七(八)）
```

### 1. 掃掠寬度 W（`sweepWidth.ts`）

未修正掃掠寬度 `Wu` 由文件表格查得（船舶 ≥46 m、EO/IR 無人機、四種飛行高度 ×
六段能見度）。能見度落在表列點之間以線性內插；低於 2 km 由原點外推，高於 40 km
取 `>40` 欄封頂。

修正因子：

- `Fw` 天候修正 — 文件僅給「風 20 kn／浪高 1.5 m → 0.5」單一錨點，故 UI 讓使用者
  直接填；`suggestWeatherFactor()` 依該錨點線性外推提供「建議」按鈕，**非文件原表**。
- `Fv` 速度修正 — 同上，文件範例用 1.5。
- `Ff` 疲勞修正 — 文件明訂 **0.9**（五(二)）。

**驗證**：文件五(二)範例（船長 100 m、500 ft、能見度 10 km、Fw 0.5、Fv 1.5）
→ `Wu = 6.4`、`W = 4.8` 浬，程式輸出完全一致。

### 2. 航跡間距 S（`patterns.ts`）

- 理想值：文件六(一)「情況許可時 S 應等於 W」→ 預設取 `S = W`。
- 條件上限（`trackSpacingCeilingNm()`）：
  - 良好（風 <15 kn 且能見度 >3 浬）→ 上限 **3 浬**（六(二)）
  - 不良（風 >15 kn 或能見度 1–3 浬）→ 上限 **1 浬**（六(三)）
  - 能見度 <1 浬 → 0.5 浬，並提示改採電子搜索（二(一)）

實際採用 `S = min(W, 上限)`；使用者可手動覆寫，超過上限時會出警示。

### 3. POD 曲線（`pod.ts`）— 由文件表 4-2 反解

文件只給 POD 圖與表 4-2 的數值，未給公式。以 Weibull 型偵測律擬合：

```
POD(C) = 1 − exp( −a · C^b )
```

- `a = 1.5141 = −ln(1 − 0.78)` — 由 C=1.0 → 78.0% 定出
- `b = 1.2539` — 由 C=0.5 → 47.0% 定出
- **獨立驗證點**：C=0.8 代入得 68.2%，文件記「約 68%」✔

累積 POD 用標準式 `1 − Π(1 − POD_i)`（七(三)、七(四)3）。以上述曲線重建表 4-2：

| 搜索階段 | 本模型 C=0.5 | 文件 C=0.5 | 本模型 C=1.0 | 文件 C=1.0 |
|---|---|---|---|---|
| 初始 R1 | 47.0% | 47.0% | 78.0% | 78.0% |
| R2 | 71.9% | 71.9% | 95.2% | 95.6% |
| R3 | 85.1% | 85.1% | 98.9% | 98.9% |
| R4 | 92.1% | 92.1% | 99.8% | 99.7% |
| R5 | 95.8% | 95.8% | 99.9% | 99.9% |

C=0.5 一列完全吻合；C=1.0 的 R2/R4 差 0.4/0.1 個百分點，源自文件本身把單次 POD
記為 78%（取 78.5% 可完全吻合）的四捨五入。

另提供古典隨機搜索律 `POD = 1 − e^(−C)` 作為保守對照模型，UI 可切換。

#### 兩條刻意的保守處理

1. **不顯示 100%** — 文件七(四)5 明訂「不得將覆蓋因子為 1.0 或 100%，直接解讀為
   發現機率為 100%」。`POD_DISPLAY_CAP = 0.999`，UI 一律顯示 `>99.9%`。
2. **C > 2 標記為外推** — 文件 POD 圖橫軸約 0–2，超出即提示數值屬曲線外推，
   並建議放寬 S 以擴大搜索面積而非重複掃同一片海。

### 4. 搜索五要素（`planner.ts`）

```
A = T × N × P × S
```

- 正解 `T = A / (N × P × S)`
- 反解 `N = A / (T × P × S)`，向上取整

**驗證**：文件七(八)範例「3 架 × 100 kt × 3 hr × 2 浬 = 1,800 NM²」，
反算 `T = 1800 / (3 × 100 × 2) = 3.00 hr` ✔

#### 滯空與架次

五要素本身不含續航限制。規劃器另計：

```
單架次可搜時數 = 滯空時數 − 2 × 單程進場時間
架次數 = ceil(掃區時間 / 單架次可搜時數)
```

滯空時數可從單位的 `extensions.endurance` 直接帶入（銳鳶 12 hr、銳穫 6 hr）。

## 三、蒙地卡羅模擬（`monteCarlo.ts`）

解析公式假設「目標在區內均勻分布且靜止、航線飛得完全精確、感測器全程可用」，
真實搜索三項都不成立。蒙地卡羅直接抽樣模擬，回答解析式答不出的問題。

### 感測器模型與兩把尺的一致性

採 Koopman 反立方律。橫向距離函數（單次通過的發現機率）：

```
p(x) = 1 − exp(−k / x²)，   k = W² / (4π)
```

`k` 由「橫向距離函數的積分必須等於掃掠寬度」定出（∫p dx = 2√(πk) = W，程式已驗證）。

**關鍵驗證**：把這條曲線代入平行航跡的多次通過幾何，算出的 POD 與文件表 4-2
擬合出的曲線高度一致：

| C | Koopman 反立方律 | 文件曲線 | 差 |
|---|---|---|---|
| 0.3 | 29.3% | 28.4% | +0.9 pt |
| 0.5 | 46.9% | 47.0% | −0.1 pt |
| 0.8 | 68.4% | 68.2% | +0.2 pt |
| 1.0 | 79.0% | 78.0% | +1.0 pt |
| 1.5 | 94.0% | 91.9% | +2.0 pt |
| 2.0 | 98.8% | 97.3% | +1.5 pt |

也就是說**文件的 POD 圖本質上就是 Koopman 反立方律**。這讓兩把尺物理上同源：
理想條件下蒙地卡羅會收斂到解析式，兩者不一致時差距就是真實效應造成的衰減，
而不是模型打架。

### 為什麼不能每個時間步各擲一次骰子

`p(x)` 是**單次通過**的機率。若每 30 秒對距離套一次 `p(x)`，靠近航跡的目標會拿到
數十次獨立機會，POD 直接灌水到 100%（開發過程實測 C=0.5 時得到 98.7%，
應為 47%）。正確做法是還原其**瞬時偵測率** γ(r) = c/r³（「反立方律」之名由來），
並要求沿直線通過的積分等於 −ln(1−p(x))：

```
∫γ dt = (c/v)·∫ds/(x²+s²)^{3/2} = (c/v)·(2/x²) ≡ k/x²   →   c = k·v/2
```

對有限線段（起訖沿航跡座標 s₁、s₂，相對最近點）有封閉解：

```
∫γ dt = (k/2)·(1/x²)·[ s₂/√(x²+s₂²) − s₁/√(x²+s₁²) ]
```

此式對步長不敏感（分 500 段累加與一次算完到小數第 8 位相同），且
s₁→−∞、s₂→+∞ 時退化回 k/x²。多架、多航段的偵測**指數可相加**，
每步再一次取 `1 − exp(−Σ)` 轉成機率（機率本身不可相加）。

### 可模擬的真實效應

| 參數 | 意義 |
|---|---|
| `driftKn` / `driftBearingDeg` | 目標漂移（風流合成）；方向可設固定或每次試驗隨機 |
| `navErrorSigmaNm` | 每架每架次抽一個固定橫向偏移，模擬風偏 / 自動駕駛誤差造成實際航跡間距不等於規劃值 |
| `sensorAvailability` | 酬載妥善率，模擬鏡頭 / 資料鏈失效 |
| `distribution` | `uniform`（解析式假設）或 `gaussian`（目標集中於基準點） |

實測（55×36 浬區、W=3 nm、S=3 nm、3 架、解析式 POD 78.0%）：

| 情境 | 經驗 POD |
|---|---|
| 理想（解析式假設） | 78.1% |
| ＋目標漂流 2 kn 隨機向 | 71.7% |
| ＋導航誤差 σ=0.5 nm | 78.8% |
| ＋感測器可用率 80% | 63.6% |
| 三者齊發 | **59.3%** |
| 目標集中基準點 σ=5 nm | 78.7% |

解析式說 78%，把三項真實效應算進去只剩 59% —— 這就是加蒙地卡羅的理由。
（導航誤差單獨看幾乎中性，因為隨機偏移在多條航段間互相抵銷；
會咬人的是感測器妥善率與漂流。）

### 統計輸出

- `pod` 與 **Wilson score 95% 信賴區間**（比常態近似在 p 接近 0/1 時可靠，
  且不會給出超出 [0,1] 的界線）
- `medianDetectionHr` / `p90DetectionHr` —— 以**全部試驗**為分母，
  百分位超過 POD 時回 `null`（誠實表示「根本沒找到」而非給個假數字）
- `podOverTime` —— POD 隨時間累積曲線，面板以 inline SVG 繪出

亂數為可重現的 LCG（`mcSeed`），同一組參數必得同一結果。

`SEARCH_PATTERNS` 收錄文件第九節速查對照表全部六種圖形的「適用情境 / 航段方向 /

### 圖形建議邏輯

| 條件 | 建議圖形 | 依據 |
|---|---|---|
| 有已知失蹤航路 | **TS** 沿航跡 | 二(一) |

天候、地形、助航設施、空域協調等因素仍須由協調官判斷，規劃器不代勞。

### 擴展方形航段表

### 航線產生

`generateSearchTracks()` 把圖形轉成每架無人機的 `LngLat[]`，可直接餵給
`scenarioStore.enqueueCommand({ kind: "set_waypoints" })` —— 引擎仍是 units 的唯一
mutator，規劃器不直接改單位。

| 圖形 | 實作 |
|---|---|
| PS | 航段平行長邊、首航跡距邊 ½S、其後每條 +1S；多機沿推進方向均分區塊 |
| CS | 同 PS 但航段平行短邊 |
| SS | 腿長 S,S,2S,2S,… 90° 轉向；多機各轉 45° 錯開（文件：重搜轉 45°） |
| VS | 三個邊長 R 的正三角形、每個轉 30°，共 9 段 ≈ 9R（符合文件「總里程 9R」） |
| TS | 航路本身 + 上下各偏移 1S 的兩條航段；多機分攤 |
| 等高線 | **不自動產生** — 需地形剖面，對應文件第十節列為「△」 |

#### 產生航線與五要素估算的差距

`A = T×N×P×S` 是理想值，不含迴轉航程，也不含最後一條航段的溢出
（`ceil(短邊/S)` 條航段的掃掠帶必然 ≥ 短邊）。實測 55×36 浬區域、S=3 浬、3 架：

- 純航段里程 718 浬、含迴轉 745 浬 → 迴轉開銷 3.7%
- 五要素估算 664 浬 → 實際多 **12.2%**

UI 會同時顯示兩個數字與差距百分比，不讓使用者誤以為估算值就是實際航程。

## 五、Stone (1983) 的貝氏框架

前四節都是「幾何」：掃掠寬度、航跡間距、圖形、航線。Stone §1 列出搜索分析者的
六項任務，指出真正把「計算機」變成「規劃器」的是另外三項 —— 事前分布、
依搜索結果更新、搜索效能。這一節就是那三項。

| Stone §1 六項任務 | 實作位置 |
|---|---|
| 1. 目標位置（與運動）的事前分布 | `targetDistribution.ts` |
| 2. 感測器能力估計 | `sweepWidth.ts`（+ 實戰效能折扣） |
| 3. 決定偵測函數 | `detection.ts` |
| 4. 擬定計畫並估算成功機率 | `optimalRectangle.ts` + `planner.ts` |
| 5. 依搜索結果更新 | `targetDistribution.ts` |
| 6. 估計搜索效能 | `targetDistribution.ts` |

### 5.1 感測器實戰效能折扣（§3）

Stone 引 Koopman [1980] p.21：**二戰經驗顯示系統在實戰情境下典型只發揮設計能力的
60–70%**，並提醒「感測器常未經測試，此時只能用設計規格，而這些估計通常偏樂觀」。

掃掠寬度表給的正是規格／測試條件下的值。現在多一個 `operational` 因子：

```
W = Wu × Fw × Fv × Ff × Fo
```

`Fo` 預設 **0.65**（Koopman 區間中值），使用者勾「感測器已在近似條件下實測」才回到 1.0。

### 5.2 偵測機率是區間，不是單點（§4）

Stone Figure 6 給了三條曲線。令覆蓋因子 C：

```
定距上界   b = min(C, 1)            航跡放置完全精確
指數下界   b = 1 − exp(−C)          Koopman 隨機搜索公式
```

Stone §4 Problem Areas 明說隨機搜索公式是「試圖均勻鋪開努力」這類搜索的
**合理下界**，實際偵測函數落在兩者之間。故 UI 一律顯示區間。

**σ/W 決定落在何處**（Figure 7）：第 i 條航跡橫向座標為常態、標準差 σ 時，
σ/W → 0 退化為定距上界；σ/W 變大時一次完整覆蓋的 POD 降到
**1 − e⁻¹ ≈ 63.2%**（Reber [1956]）—— 恰好是指數函數在 C = 1 的值。

實作以 `w(σ/W) = 1 − exp(−4(σ/W)²)` 在兩界間插值，驗證：σ/W=0 → 100%、
σ/W=1.0 → 63.9%、σ/W=2.0 → 63.21%（已收斂到地板）。

> 這也解釋了先前蒙地卡羅「導航誤差幾乎中性」的結果：當時 W=3nm、σ=0.5nm，
> σ/W 只有 0.167，落在曲線平坦段。模型是對的，只是沒把這個比值攤給使用者看。

### 5.3 掃掠寬度不確定性（§4）

W 不確定時（目標狀態未知、感測器未實測），Stone 要求對 W 給分布 {ωᵢ, βᵢ}，
並以 `b̄(t) = Σβᵢ·B(t, ωᵢ)` 當作實際偵測函數來規劃。實作為三點分布
（悲觀 / 標稱 / 樂觀，權重 0.3 / 0.4 / 0.3）。

**注意**：必須每個 ωᵢ 各自算 C 再加權，不能先把 W 平均再算一次 —— b 對 C 為凹函數，
先平均會高估（Jensen）。實測 ±40% 不確定性讓 POD 從 100% 降到 88.0%。

### 5.4 最佳搜索矩形（§5）—— 「框該畫多大」

目標為二維常態時，理論最佳的努力密度是拋物面，航空器飛不出來。Stone 退而
只考慮以均值為中心、`L₁ = 2Kσ₁`、`L₂ = 2Kσ₂` 的矩形族：

```
P_D(K) = [Φ(K) − Φ(−K)]² · [1 − exp(−E / (4K²σ₁σ₂))]，  E = W·v·t
         └─ 目標落在框內 ─┘   └──── 落在框內時被發現 ────┘
```

對 K 一維最佳化（粗掃 + 黃金分割）即得最佳框。

**驗證**：以論文範例 E = 4nm × 125kn × 3hr = 1500 nm²、σ₁=σ₂=11.25 nm，
算得 K\* = 1.468、P_D = **0.550**，與論文的 0.55 完全一致
（論文另記理論最佳計畫為 0.58 —— 簡單矩形拿到 95% 的最優解）。

框畫錯的代價（工具原本完全不提示）：

| 框大小 | P_D | 損失 |
|---|---|---|
| 邊長 ×0.5 | 0.287 | −47.8% |
| **最佳** | **0.550** | — |
| 邊長 ×1.5 | 0.433 | −21.4% |
| 邊長 ×2 | 0.289 | −47.4% |

UI 會把最佳框以綠色虛線畫在地圖上，與使用者的黃框並列，並直接給出損失百分比
與「套用最佳框」按鈕。

> **軸對齊限制**：本工具只能畫正矩形，故用邊際標準差 σ東/σ北 而非主軸 σ₁/σ₂。
> 分布主軸方位會另外顯示；相關係數 |ρ| 大時，軸對齊矩形會比主軸對齊吃虧。

### 5.5 事前分布：加權粒子（§2）

目標分布以 J 個粒子表示（CASP 表示法，p.213）：

```
(Xⱼ, Yⱼ, Uⱼ, Vⱼ, Tⱼ, wⱼ, nⱼ) = 位置、南北/東西速度、時間、權重、來自第幾個 scenario
```

N 個 scenario、第 n 個可信度 qₙ → 抽 qₙ·J 個粒子，初始權重 wⱼ = 1/J。
每個 scenario 給：基準點、位置誤差 σ、漂流速度與航向（各含標準差）。

**運動模型的取捨**：Stone 範例用 Integrated Ornstein-Uhlenbeck 過程（λ = ¼/hr）讓
洋流隨時間去相關，但他在 §2 Problem Areas 自承該模型「因資料稀少而未經檢驗，
連鬆弛率 λ 都沒有好的估計」。本實作採等速直線（λ→0 極限），**比 IOU 保守**：
以論文參數推進 11.5 小時，本實作得 σ≈12–14 浬，而由論文 P_D=0.55 反解的
有效 σ≈11.2 浬。保守方向 = 框畫得大一點、預測 POD 低一點。

### 5.6 失敗搜索的貝氏更新（§6 式 2）

```
p̃(j) = p(j)·(1 − b(j, tⱼ)) / Σₖ p(k)·(1 − b(k, tₖ))
```

搜完沒找到 → 把「本該被搜到卻沒被搜到」的地方降權，機率質量自動流向未搜區，
下一趟的最佳矩形也跟著移動。**這是規劃器與計算機的分界線**：原本工具只能提供
「同樣的搜索重複 N 次」的累積 POD，那正是這個框架要取代的天真做法。

每個粒子的 b(j) 直接用蒙地卡羅那份 Koopman 反立方律封閉解計算，
故「模擬」與「更新」不會用到兩套模型。

實測（5 趟）：POS 82% → 40% → 17% → 9% → 7%，σ東 12.7 → 21.2 浬
（分布被搜索「挖空」而變寬），累積成功機率 92.3%。

### 5.6b 搜索期中點慣例（§5）

Stone §5 處理移動目標的實務做法：

> 「這是個移動目標問題……但為保持討論簡單，我們把它當成靜止目標問題處理：
> 計算目標在**航空器搜索期中點**的分布，然後照那個分布規劃。這是實務上處理
> 搜索的常見做法。」（論文範例：遇險呼叫後 10 hr 開始搜、搜 3 hr → 取 T = 11.5 hr）

故 UI 的「基準點→抵達現場」輸入的是抵達時距，實際推進分布時會自動再加上
掃區時間的一半：`midSearchElapsedHr() = elapsedHr + sweepHr / 2`，並在畫面上
顯示實際採用的 T+ 值。掃區時間由 `solveForTime` / `solveForAssets` 算出，
不依賴粒子，故不會產生循環相依。

### 5.7 搜索效能與停止準則（§7）

Stone §7「No False Targets」：對**偵測與識別同時完成**的感測器（目視、相機、
EO/IR 皆屬此類），事前發現機率 P 本身就是很好的效能指標 —— 不需要 SEP。
Stone 還指出 SEP 有個病態：一旦取得接觸 Eⱼ = 0，SEP 反而下降，
「本該是好消息的事卻讓效能指標退步」。

停止建議直接引 Stone 的論證：

> 「P 高（如 0.9）意味著在假設條件下重複同樣的搜索，九成會找到目標。因此失敗
> 是運氣不好或假設有誤，而非規劃不當 —— 我們已經用盡了搜索所依據的資訊；
> 若無新情報，就該停。當然，"高" 的定義是主觀的。」

門檻可調（預設 0.9）。

## 六、已知限制

- **搜索區為正矩形框**（東西 / 南北軸對齊），與既有聲標屏幕同慣例。斜向長軸的
  搜索區需自行分割成多個框。
- **掃掠寬度表只涵蓋船舶 ≥46 m**，這是文件提供的範圍。小型目標（救生筏、
  落水人員）需另補表。
- **Fw / Fv 無完整對照表** — 文件各只給一個錨點，UI 預設 1.0 並提供建議值按鈕，
  實際數值應由協調官依現場狀況填入。
- **地形遮蔽未納入** — 掃掠寬度不因陸地 / 山區遮蔽而折減；文件三(一)的地形影響
  目前只能透過手動調低 Fw 反映。
- **蒙地卡羅不模擬多次搜索** — 目前只跑一輪航線。重複搜索的累積 POD 仍走解析式
  `1 − Π(1 − POD_i)`。
- **漂流為等速直線** — 未模擬隨時間變化的流場，也未把漂移後的目標重新框回搜索區
  （目標漂出區外即等於漏失，這與文件三(二)「須注意漂流使目標漂出區外」的警告一致）。
- **未實作假目標（Stone §6）** — Stone 用每格 Poisson 參數 δ(j) 模擬與目標偵測特性
  幾乎相同的物體。對海上無人機搜索這很真實（IAMSAR 文件本身就提到海藻、油膜、
  漂浮物會被誤認為救生筏），每個假接觸都會吃掉查證時間。目前完全未計入。
- **最佳矩形限軸對齊** — 見 5.4 的說明。
- **粒子機率圖未平滑** — Stone §2 Problem Areas 引 Weisinger [1978]：蒙地卡羅取樣
  噪訊會劣化規劃建議，平滑會改善，但當時沒有滿意的方法。本實作同樣未平滑，
  只以足夠粒子數 + Wilson 信賴區間表達不確定性。
- **多趟之間不重新推進漂流** — 貝氏更新只更新權重，未把粒子再往前推進到下一趟的
  時刻。長時距的多趟搜索應在每趟之間呼叫 `propagate()`。（單趟內的目標運動已由
  5.6b 的搜索期中點慣例涵蓋。）

Stone 論文中明列、至今仍屬開放的問題（本工具同樣未解，UI 不應把相關數字講得太篤定）：
主觀機率的系統化萃取、蒙地卡羅平滑、洋流模型參數、移動目標的簡單近最佳計畫、
帶信賴區間的橫向距離函數估計、偵測模型中的虛警率、單調遞增的 SEP 定義。

## 七、語言

引擎完全語言中立：`planner` 回傳 `PlannerNotice { code, params }`、
`pod` 回傳 `CoverageLevel`、`patterns` 回傳 `PatternReasonCode`，
六大圖形說明則以 `zh` / `en` 兩份 `PatternText` 並存。
所有面向使用者的字串在 `search/i18n.ts` 產生，新增語言只要多一份 `SearchStrings`。
語言由既有的 `wargame/i18n/lang.ts` store 控制，兵推與獨立 app 共用同一個切換。
